# 硬件占用优化方案（评估稿）

> 2026-08-11 实测数据，**先不改动**。目的：降低服务启动后的 CPU / 内存 / 显存占用。
> 读完本方案后请选择要实施的方向（可组合）。

---

## 一、现状测量（真实数据）

**启动后服务器进程占用**（WSL2，16 页文档场景）：

| 指标 | 数值 | 说明 |
|------|------|------|
| **Python 进程 RSS** | **4.28 GB** | 用户视角的"内存占用大"主因 |
| 系统内存实际占用 | ~2.5 GB | 减去共享库后的真实增量 |
| **GPU 显存** | **1.6 GB** | warmup 加载的 reranker + CUDA 上下文 |
| 启动耗时 | ~1s 完成导入 | 导入期 CPU 有峰值 |

**内存构成拆解**（实测逐步导入）：

| 来源 | 内存 | 累计 |
|------|------|------|
| 基线 | 11 MB | 11 MB |
| `import torch` | +484 MB | 495 MB |
| `import sentence_transformers` | +311 MB | 865 MB |
| `import paddle` | +494 MB | 1389 MB |
| **ML 库导入合计** | **~1.38 GB** | |
| + warmup 常驻模型（embed + reranker） | ~1 GB | ~2.4 GB |
| + torch CUDA 上下文 / CUDA 运行时映射 | ~1 GB | ~3.4 GB |
| + 其他依赖 / 开销 | ~0.9 GB | **~4.28 GB** |

> ⚠️ 核心洞察：**大头不是模型权重，而是"启动时全量导入 ML 库"**。easyocr 导入虽轻（+30MB），但其模型按需加载；真正贵的是 torch / paddle / sentence_transformers 这三个库的**静态导入**。

---

## 二、优化方案

### 方案 A：延迟导入重型 ML 库（Lazy Import）⭐ 推荐

**做法**：现在 `create_app()` → 路由 → orchestrator 在**模块导入时**就把 torch/paddle/easyocr/transformers 全拉进来了。改为在这些库**首次使用时才 import**（把模块顶部的 import 移到函数内）。

**收益**：服务器基础 RSS 从 4.28GB → **约 1~1.5GB**（省 ~3GB，主要是导入成本）。首次请求时补付一次导入（~1-2s CPU）。

**投入**：中（把 orchestrator 及下游的顶层 import 改为惰性，约 10-20 处）。
**风险**：低-中（需保证首次调用路径都正确导入；对并发首请求有一次性导入竞态——需加锁）。

### 方案 B：warmup 可配置 / 关闭 ⭐ 推荐

**做法**：启动时的模型预热（迭代 10 加的）改为可配置 `WARMUP_MODELS=false` 关闭。

**收益**：省 embed + reranker 常驻内存 ~1GB + GPU 1.6GB。**代价**：首个查询慢 ~5s（要现场加载模型）。

**投入**：低（一个设置项）。
**风险**：低。适合"服务器常驻但查询频率低"的场景；查询频繁则不值得关。

### 方案 C：模型按需卸载（查询/处理后释放）

**做法**：查询/文档处理完成后调用 `unload()` 释放 reranker / embed，下次用时重载。

**收益**：空闲时内存回到 ~1.5GB。**代价**：每次请求多付 ~1-3s 重载，GPU 反复初始化。
**投入**：中。
**风险**：中（与并发请求冲突——多个请求同时用模型时卸载会破坏）。**适合单用户低并发**。

### 方案 D：轻量化 OCR 依赖（替换 easyocr）

**做法**：easyocr 模型实际加载 ~1GB+。换成更轻的 OCR（如 PaddleOCR 单模型 / ONNX 轻量 OCR）或按需加载。

**收益**：处理扫描件时省 ~0.5-1GB。
**投入**：中-高（识别质量需回归）。
**风险**：高（OCR 质量可能下降）。**非当前主要矛盾**（启动时 easyocr 模型并不加载）。

### 方案 E：组合 A + B（推荐首选）

延迟导入（A）+ 关闭 warmup（B）组合：
- **服务器常驻 RSS：4.28GB → ~1GB**
- GPU 显存：1.6GB → ~0（不加载模型）
- 首个查询：+~5s（模型首次加载，之后正常）
- 文档处理：首次 +~5s，之后正常

**最适合"服务挂后台、偶尔查询"的用法**；若你高频查询，可只开 A 保留 B 的 warmup。

---

## 三、建议执行顺序

| 优先级 | 方案 | 收益 | 投入 | 适合 |
|--------|------|------|------|------|
| ① | **E（A+B 组合）** | 内存 4.28→1GB，显存清零 | 中 | 常驻低查询 |
| ② | 仅 A（保留 warmup） | 内存 4.28→~2.5GB | 中 | 高频查询 |
| ③ | C 按需卸载 | 空闲更低 | 中 | 单用户 |
| ④ | D 轻量 OCR | 处理时省 1GB | 高 | 扫描件多 |

---

## 四、权衡提醒

- **内存 vs 响应速度**是本方案的核心取舍：省内存 = 首次请求慢几秒。
- 本项目模型加载耗时：embed ~9s（ONNX 已持久化，热加载）→ 实际 ~2s；reranker ~1s。所以"关闭 warmup"的实际代价是首查询多 ~3-5s，之后无差别。
- 若你机器是 8GB/16GB 且服务常开，方案 E 收益最明显；若查询很频繁，选 A 单独保留 warmup。
