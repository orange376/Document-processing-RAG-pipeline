## 迭代 4 — 切片质量与图表解析修复

**日期**：2026-07-25 ~ 08-01
**Git**：`067f206`、`a2929e6`

### 切片重写（`067f206`）
- **根因**：句子级切分太碎、选择题选项孤悬、短标题独立成块、多题挤一块
- **修复**：一道题 = 一个块；ABCD 选项黏合题干；`填空题`等短标题合并；块内多题拆分
- **效果**：高数模拟题 71 chunks → **44 chunks**，每块都是完整语义单元

### 公式图片识别（`067f206`）
- **根因**：MathType/Equation Editor 的 VML WMF 图片（109/116）漏检；WMF 低分辨率渲染
- **修复**：新增 VML `w:object→v:imagedata` 检测路径；从 docx zip 直接读原始 WMF 高分辨率渲染；图片放大到 600px；并发批处理
- **效果**：116 张公式图片全部检测 + 并发识别

### PDF 图表描述（`067f206`）
- **根因**：PP-DocLayoutV3 返回对象而非 dict 导致版面分析静默失败（BBox 缺 page_num）；图表描述用了文字模型 404
- **修复**：PaddleX 对象兼容 + BBox 修复；Qwen-VL 直连 + image_url 发图
- **效果**：架构图/功能模块图/ER 图全部转成可检索文字（8 个 figure chunks）

### Qwen-VL 404（`a2929e6`）
- **根因**：`LLMClient(provider="qwen")` 用了文本模型 `qwen3-7b-plus`（404）；算了 base64 却没发图
- **修复**：新增 `chat_with_image()` 用 `qwen_vl_model` + data-URI 发图；表格恢复复用

## 迭代 6 — WSL2 GPU 迁移

**日期**：2026-08-01 ~ 08-10
**Git**：`9106a56`、`5caebbb`

### 背景
- 机器有 RTX 4060 (8GB) 但 Windows 端 torch 是 CPU 版
- 用户选定 GPU 推理，接受 WSL2 路径（Linux 下 paddle GPU/torch CUDA wheel 支持更好）

### 迁移步骤（详见 `docs/WSL2-GPU部署指南.md`）
1. **uv + Python 3.12**：系统 Python 3.14 不支持 paddle，用 uv 装 3.12（免 sudo）
2. **torch CUDA**：pytorch.org 索引 + nvidia 依赖走清华镜像（pypi.nvidia.com 从国内超时）
3. **paddle 3.3.1 GPU**：官方 cu126 索引；与 torch 的 nvidia 版本冲突已调和（升回 torch 版本两者兼容）
4. **libgomp**：paddle 找不到 → 用 torch 自带 `torch/lib/libgomp.so.1`
5. **模型**：bge-base-zh/reranker via HF 镜像；pix2tex 权重 via ghproxy 代理；reranker 文件结构修正
6. **.env**：从 Windows 复制 API keys

### 实测性能（WSL2 GPU）
| 指标 | Windows CPU | WSL2 GPU | 提升 |
|------|-------------|----------|------|
| 17页 PDF 版面分析 | 167s | **16s** | **10 倍** |
| 整文档处理 | ~8 分钟 | **58s** | **8 倍** |
| 问答 | — | 0.799 置信度，5 引用 | ✓ |

### 关键修复
- WSL 空闲停止（清 /tmp）→ 服务器放后台任务保持会话
- `HF_ENDPOINT` 缺失导致模型加载卡死 → 固化到 venv activate
- ONNX 导出在 WSL2 卡 13 分钟 → 直测确认是 HF 网络问题

### 1. 测试套件全绿（`214 passed / 0 failed / 0 errors`）

| 修复 | 根因 | 方案 |

| `test_retriever::test_retrieve_successful_flow` | `retrieve()` 新增 `source_files` kwarg 后断言过期 | 断言补 `source_files=None` |

### 2. ONNX 导出持久化（省启动 ~35s）

- **根因**：ST 5.6 按 **hub id** 加载模型时，`backend_should_export` 检查的是**远端仓库**有没有 `*.onnx`（永远没有）→ 每次进程启动都重新导出（26~43s）
- **修复**：改用 `snapshot_download(local_files_only=True)` 解析本地快照路径加载 → ST 检查本地目录 → 首次导出后 `save_pretrained()` 持久化 `onnx/model.onnx`（406MB），之后跳过导出
- **坑**：`**/*.onnx` glob 会把备份目录误判为已持久化 → 改为精确检查 `onnx/model.onnx`
- **实测**：冷启动（导出+持久化）43.9s→14.2s；热启动（跳过导出）8.9s

### 3. `[stage]` 日志丢失——根因定位 + 心跳补强

- **结论**：不是日志系统 bug。WSL2 日志 2 份文档各阶段记录完整；老日志的"丢失"是**处理挂起**（Qwen-VL 404 重试 291s、ONNX 导出 235s、HF 网络），进程卡在两阶段之间没往下走，这些根因已随迭代 5/6 修复
- **补强**：orchestrator 每个阶段加 `[stage] X: starting` 心跳日志（layout/describe/ocr/tree_build/chunk/embed+index），长阶段期间有可见进度；OCR 阶段补了结束计时日志

## 迭代 8 — Redis 缓存激活 + 改写确定性修复

**日期**：2026-08-10
**Git**：`d4e12b4` → `3231360`

### 1. 启动 Redis（免 sudo，apt 安装）

- WSL2 无 systemd，`redis-server --daemonize yes` 直接跑；`sudo` 用用户提供密码安装
- 三级缓存激活：embedding(7d) / reranker(1h) / answer(1h)，版本化 key

### 2. 🔥 发现并修复：改写非确定性导致缓存永久失效

**复现**：三次相同查询各新增 30 个 rerank key、1 个 answer key —— 缓存全部 miss，重复查询仍 ~30s。

**根因**（两层）：
1. `QueryRewriter` 用 LLM 默认温度 0.3 改写 → 同一 query 每次改写结果不同 → rerank key（`md5(改写|chunk_id)`）和 answer key（context）永不对上
2. **即使 temp=0，实测 DeepSeek 改写仍不确定**（两次输出不同）

**修复**：
- 改写结果按**原始 query** 记忆化（Redis `rag:rewrite:*` + 进程内 memo）
- 同一原始查询 → 稳定改写 → 稳定检索 → 相同 context → 下游缓存全部命中

**实测**（三次相同查询）：

| 次数 | 耗时 | 说明 |
|------|------|------|
| 第 1 次 | 42.7s | 全流程（改写+检索+重排+LLM） |
| 第 2 次 | **2.3s** | answer 缓存命中（**18 倍提速**） |
| 第 3 次 | **2.3s** | 命中 |

Redis 落库：**1 answer + 30 rerank + 1 rewrite**，后两次零新增 key。

### 3. 配套测试

- `test_rewrite_memoized_same_llm_called_once`：同 query 只调一次 LLM
- `test_rewrite_memo_distinct_per_query`：不同 query 不共用缓存
- 隔离真实 Redis（WSL localhost 镜像会让 Windows 测试连到 WSL Redis）

## 迭代 9 — 查询扩展修复低置信度拒答（看效果时发现）

**日期**：2026-08-10
**Git**：`f5888a1`

### 现象

演示时发现：答案内容完美（5 个真实引用），但置信度只有 0.274 < reject 0.40 → 被降级拒答（"当前回答的置信度较低"）。

### 根因链（三层）

1. **bge-reranker-base 是词面重叠敏感模型**：实测问题式查询对相关 chunk 只有 0.002-0.02，关键词式（含文档术语）0.86-0.99
2. **QueryRewriter 产出通用关键词**（"技术方案/技术路线/解决方案"），不含文档具体术语（架构/B/S/C/S）→ 对文档 chunk 仍只有 0.015
3. **查询时置信度 = 0.6×reranker_max + 0.4×coverage** → reranker_max≈0.12 时整体 0.27，永远低于 0.40 阈值

### 修复：查询扩展（Query Expansion）

`retriever.py` 在 rerank 前，用 jieba 从 top-5 候选 chunk 提取高频领域词（≥3 词才扩展），追加到 rerank query：

- 原始：`文档中提到了什么技术方案？` → reranker 0.002
- 扩展：`文档中提到了什么技术方案？ 架构 基础设施 存储 前端 ...` → **0.937**

### 效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 置信度 | 0.274（拒答） | **0.762（accept，needs_review=False）** |
| reranker 分 | 0.123 | **0.937** |
| 答案 | 降级消息 | 完整回答 + 5 引用 |

### 附带修复

- **jieba 未声明依赖**：Windows venv 缺失（BM25 也用它）→ 加入 pyproject

## 迭代 10 — 查询性能优化：模型预热 + 表格并发

**日期**：2026-08-11
**Git**：`2356ea6` + warmup 日志

### 剖析

冷查询耗时拆解（实测）：

| 场景 | 耗时 |
|------|------|
| 重启后首次查询（冷） | **51.6s** |
| 热模型 + 无答案缓存（新问题） | 18.4s |
| 热模型 + 答案缓存 | 2.7s |

**瓶颈**：重启后首次查询的 ~33s 是**模型懒加载**（embed ONNX ~9s + reranker ~1s），叠加 LLM 重写+回答 API 耗时。

### 优化 1：启动时后台预热模型

- `query.warmup()` 在 FastAPI lifespan 启动时用 `asyncio.to_thread` 后台加载 embed + reranker 单例模型
- 消除首次查询的模型加载惩罚，启动不被阻塞（后台任务）
- **实测：冷查询 51.6s → 17.3s（3 倍）**，剩余耗时纯 LLM API

### 优化 2：表格恢复并发化

- `_recover_tables` 原来逐表串行 `await` Qwen-VL（每表 2-4s）
- 改为先收集全部表格裁剪图，再 `BATCH=4` 用 `asyncio.gather` 并发识别
- 多表格文档处理提速明显（识别调用是处理瓶颈）

- 迭代日志补 warmup 成功日志（可观测性）
